Auditing + wiring the **whole agency role** to the backend (beyond roster — see [[roster-backend-wiring]]). Approach chosen by user 2026-07-19: **Hybrid** — per screen, wire the reads to real data + the CRUD the backend supports; leave demo-only rich fields as cosmetic placeholders (same tradeoff as the roster grid).

**Audit finding (definitive, by import grep):** the ENTIRE agency portal is demo-store-driven EXCEPT the roster planning view. Backend `@/services/*` calls appear only in roster files. Every other screen uses `useStore` (demo). BUT backend services already exist for most domains — it's a wiring job. Routes are thin: `dashboard.tsx`→redirect /agency, `live.tsx`→redirect /agency/roster.

**Backend is thin CRUD vs rich demo screens.** e.g. Manage PR = ~40 demo fields (`AgencyManagedPR`) but backend `pr` has only name/nickname/tier/status/phone/email/icNo + create/update(PUT)/delete. So each screen wires ~6 fields; the rest stay placeholder. Backend enums: `pr` tier `tier_1|tier_2|tier_3`, status `active|inactive|pending|suspended`.

**Wiring pattern (established, reuse it):** 1) add missing service wrappers (the backend often has update/remove the frontend service lacks); 2) a `*-map.ts` mapper thin-backend→rich-demo shape with placeholders; 3) a `use-*.ts` hook (fetch+map+mutations, invalidate); 4) swap the screen's `useStore` data source + mutation callbacks for the hook, keep demo reads for cosmetic sections. Keep the file's existing quote style; don't whole-file reformat prototype screens (they carry pre-existing biome format findings — leave them).
